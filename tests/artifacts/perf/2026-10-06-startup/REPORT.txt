Coreutils startup investigation — 2026-10-06

The complaint reproduces on wx-workstation. In the initial, lower-load runs,
Rust multicall true is 3.00x GNU and multicall ln -sf is 2.65x GNU by median
elapsed time. Standalone Rust executables substantially reduce that gap,
but still cost 1.88x and 1.80x GNU respectively.

All compilation, correctness tests, benchmark execution, instrumentation,
profiling, and statistical analysis ran through ssh wx-workstation. The Mac
was used to read the uutils source, prepare scripts, and retain these results.
No GNU implementation source was read or copied. No production source change
was made; the two files instrumented in the remote copy were restored and
their Git blob hashes match the local checkout.

TIMING RESULTS

Warm filesystem caches; LC_ALL=C and LANG=C; inherited affinity to CPU 4;
hyperfine -N (no shell) with 10 warmups. Explicit executable paths prevent
accidentally benchmarking the shell's true builtin. ln always replaces an
existing dst.txt symlink to src.txt. Creation and replacement were verified.
The benchmark runs in a fixture directory outside the source tree, with no
external locale files, so Rust uses its embedded English resources.

Initial forward/reverse sweeps: 2 x 2,000 launches per executable/workload.
All values below are microseconds. No outliers were discarded.

There was one 43.8 ms outlier in GNU ln's first sweep; median is the primary
statistic. Full distributions, p99, p99.9, p99.99, maximum, and launch rates
are in baseline-summary.json. Extreme percentiles are weak estimates:
4,000 samples contain only about four observations beyond p99.9 and fewer
than one beyond p99.99. Do not treat them as reliable tail guarantees.

The median multicall-minus-standalone difference is almost identical for
both utilities: 178.6 us for true and 181.0 us for ln. Most of that difference
is common process startup, rather than the actual link operation.

Instruction percentages are inclusive USERSPACE INSTRUCTION counts under
Callgrind, not elapsed-time percentages, cycle samples, or kernel profiles.
Nested functions (e.g. relocation within loader, parsing within localization)
must not be added together. Native stage probes are a separate build, gated
for reporting by UUTILS_STARTUP_PROFILE=1. They never supplied the baseline
timings. Timer calls perturb tiny stages, so sub-microsecond values should
be interpreted as approximate.

The Rust true utility itself takes about 0.8 us multicall / 0.4 us standalone
once entered. It pays localization before doing essentially no useful work.

FOOTPRINT, DISK I/O, AND ALLOCATIONS

Sample unprofiled /usr/bin/time -v results:
                         GNU true      Multicall true      Standalone true
Minor faults             68            353                 119
Major faults             0             0                   0
Max RSS, KiB             1052          5200                2088
Block reads              0             0                   0

ln: GNU 76 minor faults / 1024 KiB RSS; multicall 379 / 6184; standalone
139 / 2096. These RSS/fault figures are single-run samples, supported by
separate repeated resource accounting. The accounting harness also includes
the Python child's pre-exec fork overhead and should not be used as a pure
executable CPU-time measurement. No measured case needed major page faults
or block reads in this warm-cache experiment. Cold-cache behavior was not
measured, and no global cache drop was performed.

Heaptrack observed 218 allocation calls for multicall true and 217 for
standalone true, versus 1 in the GNU true control; multicall ln made 476.
Fluent parsing/bundle construction appears prominently in their stacks.
Reported high-water heap: ~134 KB for Rust true and ~176 KB for Rust ln.
Heaptrack has preload/constructor overhead (including ~74 KB seen even in
GNU true); these are instrumented-process figures, not net utility-only
allocations. Process-lifetime cached resources retained at exit are not
automatically evidence of a leak bug. Heaptrack RSS includes profiler memory.

The profiling multicall file is 63,618,656 bytes with debug data, and
15,782,128 bytes after strip --strip-debug. Same loaded implementation:
means 502.3 vs 502.8 us, medians 487.5 vs 494.7 us. There is no material
speedup from removing debug-file bulk. Relevant factors are mapped/touched
pages, relocations, additional libraries, and initialization work, rather
than raw file size alone. The multicall has libgcc_s, libm and libc as NEEDED
libraries; GNU true/ln only list libc. Stripped size is not a cold-I/O test.

HYPOTHESIS LEDGER

Supported: multicall packaging adds a large shared startup cost; similar
true/ln deltas, far more relocations, and hundreds more minor faults.
Supported: eager localization is substantial on success/no-output paths;
native timings, allocation stacks, and instruction profiles agree.
Supported: Rust std initialization contributes independently of uutils;
empty-program comparison and stack/signal/syscall profiles agree.
Supported: Clap construction/parsing adds ln-specific overhead.
Small contributor: dispatch/search by executable name, measured ~7 us.
Not supported as the warm-cache explanation: reading the full large file
from disk; no block reads/major faults, and stripping debug data did not help.
Not observed: lock contention, worker-thread waits, or fsync stalls.
Unresolved: exact allocation of elapsed time among kernel exec, mapping,
page faults, process teardown, scheduling, and userspace startup. We have
userspace instruction attribution and native stage measurements, not a
complete additive kernel+userspace wall-time decomposition.

PROFILER LIMITS AND VALIDATION

perf_event_paranoid is 4; sudo is unavailable without a password. Both samply
and software perf sampling were denied. The /usr/bin/perf wrapper also lacks
a matching kernel package; using the available perf binary did not overcome
the access restriction. No kernel settings or governors were changed.
Callgrind, strace, LD_DEBUG=statistics, heaptrack and native probes provided
the evidence above. Raw loader statistics retain their reported "cycles"
unit; this report does not convert them into an end-to-end wall-time budget.

Correctness: all six initial cases return status 0 with no output; all ln
variants create and replace the exact requested symlink. The unmodified
remote source passed all 7 test_true tests and all 60 test_ln tests using:
  cargo test --locked --no-default-features --features 'true ln' test_true::
  cargo test --locked --no-default-features --features 'true ln' test_ln::
See smoke-tests.txt, test-true.log and test-ln.log.

REPRODUCING / CONTINUING THE COMPARISON

Keep separate GNU / Rust multicall / Rust standalone results in every
future run. Record any changes to build features, target, locale, invocation
style, packaging, or linker flags; they can affect startup independently.

Baseline build in the remote source directory:
  CARGO_PROFILE_RELEASE_DEBUG=1 RUSTFLAGS='-C force-frame-pointers=yes' \
    cargo build --locked --release --features unix \
      -p coreutils -p uu_true -p uu_ln --bin coreutils --bin true --bin ln

Copy the resulting uninstrumented executables to bin/multi and bin/single
before any probe build; symlink bin/multi/true and bin/multi/ln to coreutils.
Run these scripts only on wx-workstation, sequentially:
  python3 artifacts/measure.py
  python3 artifacts/profile.py
  bash artifacts/controls.sh
  python3 artifacts/interleave.py
The paths in the scripts deliberately point at the remote work directory.
profile.py expects the privately extracted Valgrind package under
tools/valgrind, avoiding system package installation.

instrument.py applies measurement-only native stage probes to the disposable
remote source. Build with the same release flags, preserve those binaries
separately, collect UUTILS_STARTUP_PROFILE=1 runs, then restore the files from
the original-* backups. instrumentation.patch contains the full probe diff.
analysis.json, baseline-summary.json and raw JSON preserve the distributions;
*.callgrind / *.instructions-*.txt preserve instruction attribution;
*.strace and *.elf.txt preserve syscall and binary metadata evidence.

The next optimization candidates, if requested, are reducing the multicall
relocation/touched-page footprint and deferring localization until required.
This investigation made no optimization changes.
